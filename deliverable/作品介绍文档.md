## 一、作品概述

一个跑在黄山派（SiFli SF32LB52）开发板上的**端云协同语音 Agent**：

对着板子说话，设备负责采集与执行，PC 负责理解与推理，屏幕用中文回话；
同时它按计划**主动巡检设备状态**，不需要任何人开口。

一句话卖点：**在一块没有网卡、没有桌面系统的裸机上，
用一根 USB 线实现了「语音进、执行出、中文上屏、主动汇报」的完整 Agent 闭环。**

2026-11 增补：设备端新增**健康监测与自治恢复**——无人值守时也能自己发现麦克风停采、
线程卡死、网络掉线或内存异常，先重启服务、必要时门禁内软复位，并把复位证据留在 RTC 备份寄存器。

## 二、目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 嵌入式开发者 | 对着开发板口述指令完成巡检（"看一下设备内存"），不必连串口敲命令 |
| 智能终端用户（手表/桌面设备） | 设备无人值守时按计划自检并主动汇报异常 |
| 展会/教学演示 | 无网络环境下依然可完整演示（本地 ASR + 可切 mock LLM） |

**痛点**：现有嵌入式 AI 演示普遍是"连着电脑敲命令"或"必须联网才有反应"。
本作品解放了两端——设备端无按键启动、**喊一声唤醒词即可开口**；网络端可降级到本地模型，演示不中断。

## 三、用户故事（4 个）

### 故事 1：语音下命令
> 我喊一声"**你好openvela，现在几点了**"，屏幕随即显示当前时间；
> 再说"**你好openvela，看一下设备的内存**"，屏幕显示内存占用。
> **全程手不用碰板子**——也不需要电脑、不需要键盘。
> （不方便开口时，也可以点屏幕上的 PTT 按钮：点一下开始说、再点一下结束。）

### 故事 2：主动巡检（核心差异化）
> 我说"**请每两分钟巡检一次设备**"。之后我什么都不做，每两分钟屏幕上自动出现一条巡检结果
> （内存、任务数、链路状态），PC 端同步收到。设备无人值守时也在工作。

### 故事 3：断网可用
> 展会上网络断了。设备与 PC 的链路不受影响（走的是本地 PPP 链路而非互联网），
> LLM 通道降级到本地剧本模型（`proxy_restart.sh` 启动时带 `--fallback-mock`，
> API 不通会自动降级），语音识别全程在本地完成，**演示不中断**。

### 故事 4：屏幕即回执
> 每一次语音指令、每一次巡检、每一次错误，都会在屏幕聊天流里以中文气泡显示，
> 不用连串口看日志就知道设备在做什么。

## 五、技术实现

### 5.1 系统架构

```
┌─────────────────────── 黄山派 SF32LB52 ───────────────────────┐
│  MEMS MIC → AUDCODEC ADC → μ-law 编码 → WS 二进制帧           │
│  LVGL 四页 UI（时钟/对话/状态/设置，中文） ← 消息总线 ← agent 核心 │
│  主动任务（cron）        →  到点自动巡检 → 上屏 + 上行         │
└──────────────────────────┬───────────────────────────────────┘
                           │ PPP over 串口（实测 12.7 KB/s）
┌──────────────────────────┴───────────────────────────────────┐
│  PC（云侧）：PPP 服务端 + NAT + 串口桥                         │
│   语音桥：VAD → 离线 ASR（Paraformer）→ 命令路由               │
│   LLM 代理：设备明文 HTTP → HTTPS（DeepSeek 等）/ 本地 mock    │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 使用的 ai_agent 核心能力

| 能力 | 本作品的使用方式 |
|---|---|
| **消息总线** | 新增 UI 通道接入：agent 的每一次回复镜像到 LVGL 屏幕；`internal` 标志区分系统事件 |
| **主动任务（cron）** | "每两分钟巡检一次"即注册一条 cron 任务，到点唤醒 agent 执行工具链 |
| **Tool 调用** | 时间查询、内存/任务读取、定时任务管理等工具，由 LLM 自主选择调用 |
| **Router 意图路由** | 语音转写 → 命令路由分流（控制类命令 vs 对话类请求） |
| **多渠道** | 语音（WS）、文本（WS）、REST、屏幕四条通道并存 |
| **Skill 体系** | 12 个内置技能随固件生效；修复了技能描述解析缺陷（上游 A23） |
| **健康状态**（2026-11） | 新增 `health_monitor` 线程、`get_health` 工具与 WS `health` 告警；agent 可主动查询设备健康，`device-guardian` 技能优先使用它 |
| **模型来源**（2026-11） | 设置页可在本地 mock 与云端 LLM 之间切换；设备只换自己的 `llm_port/model`，PC 同时跑 8081/8080 两个端点，真实 key 不离开 PC |

### 5.3 三个关键技术决策

1. **码率预算驱动的音频设计**：实测串口链路只有 ~12.7 KB/s（CH340 + USB/IP 的物理上限），
   16 kHz×16 bit 需要 32 KB/s 根本传不动。改用 **G.711 μ-law 单字节/样本 @8462 Hz
   ≈ 8.46 KB/s**，再重采样到 16 kHz 喂离线 ASR——**60 秒 soak 交付 8.40 KB/s、0 丢包**。
   也试过 17.4 kHz / 4-bit IMA ADPCM（约 8.7 KB/s），连续流超出链路约 8%，暂未采用。
2. **无头 + 无竞态启动**：`ai_agent < /dev/null`（读 EOF 即退出 CLI 线程）+ `pppd` 前台运行
   （NSH 阻塞在 waitpid，不再与控制台争抢），一条命令完成启动，无需人工交互。
3. **PC 代理 LLM**：设备端 TLS 路径在 16 KB 以上不可靠（上游 A20），改为设备走明文 HTTP
   到 PC，由 PC 代理转 HTTPS——顺带获得了"断网切 mock"的演示能力，**真实 API Key 从不进设备**。
   2026-11-04 已用真实 DeepSeek 实测通过（`deepseek-chat`，首轮约 2.8 s）；同时修复了
   REST 下发配置只刷新 router、不刷新 `llm_proxy` 静态 key/port 导致的"有配置但不出网"问题。
   设备设置页新增「模型来源」切换：PC 同时跑本地 mock（8081）和真实代理（8080），
   设备只切自己的端口/模型，真实 key 始终不出 PC。

### 5.5 端侧健康与自治恢复（2026-11 扩展）

设备端每 5 s 采样一次，形成统一快照：`status`（starting/ok/degraded/critical）、
`issues[]`、堆/任务/网络/WS/麦克风/cron/LLM/消息总线分组，以及每个线程的心跳年龄。
规则覆盖堆低/碎片/趋势、线程停顿、WS accept 死亡与发送失败、麦克风停采、网络掉线、
cron 停摆、LLM 失败/过慢、总线积压；每条规则有独立去抖与滞回。

恢复顺序：**重启 mic → WS listener-only 重启 / drop 问题 client → 门禁内软复位**。
软复位需同时满足：critical 且属可复位类、uptime ≥120 s、复位预算未耗尽、网络曾 up
（或断网 ≤120 s）、非 safe_mode；第 2 次起还要求设备已存活 ≥300 s，避免复位风暴。
复位前把 boot 次数、复位原因（`health_auto`）、最近异常摘要写入 RTC BKP5/BKP6，
回读校验后置 `persist_ok`；连续 3 次后进入 safe_mode，主机 `POST /api/health/ack` 清除预算。
软复位会丢 `/data`，主机 `voice_ready.sh --no-reset` 重新下发配置并 ack。

2026-11-04 HIL 结果：mic 读失败 3 次后自动重启恢复；agent 停顿 45 s 触发 degraded 后自恢复；
net_down 60 s 只告警不复位；WS 发送失败 20 次触发 warning 并 drop 问题客户端；
heap_hog 触发 heap_trend critical 后 `health_auto` 软复位（boot=2）；
永久 agent stall 触发 task_stall critical 后软复位（boot=3）。两次复位均 `persist_ok=true`，
`last_anomaly` 分别为 `heap_trend` / `task_stall`。设计与完整记录见
`docs/health-subsystem.md`。

## 十、局限与下一步

- **平台已知缺陷：设备会间歇性挂死**（属 openvela/NuttX 内核问题，非本作品代码）。
  定位到 `nuttx/sched/semaphore/sem_waitirq.c:137` 的断言——信号量「超时 vs post」竞态，
  触发点在 TCP 接收路径（每次 LLM HTTP 请求都会经过）。
  **已排除栈溢出**（开了 `CONFIG_STACK_CANARIES` 未触发，加大各线程栈也无改善）。
  挂死表现为屏幕冻结 + ping 不通，复位即可恢复，不影响作品功能本身。
  2026-11 的健康子系统已能发现这类症状并先尝试服务级恢复、必要时门禁软复位；
  WS accept 循环改为非阻塞轮询以绕开该竞态的典型触发路径，其余 timed wait 的根因修复属内核范围。
  已作为平台缺陷单独记录，建议上游修复。
- **safe_mode 未做完整 HIL**：连续 3 次门禁软复位后进入 safe_mode 的逻辑已实现，
  但完整验证需要约 15–20 分钟（第 2 次起要求 uptime ≥300 s），留作后续；
  主机 watchdog 的 1 h 空跑 soak 同样待补。
- **BBRAM 不跨掉电**：RTC 备份寄存器在拔电/重新烧录后会丢，软复位可保持；
  生产中若需跨掉电证据应落 NVS。
- 唤醒词受限于 8462 Hz 采样带宽（奈奎斯特上限约 4.2 kHz）：`openvela` 中的 /v/、/l/
  仍不稳定，识别器会转写成 open villa / open vlog / 欧朋 等变体；匹配规则采用「品牌任意位置 + 别名纠错」。
- LLM 通道依赖 PC 代理（属演示架构；产品化应内置 TLS 修复或走端侧小模型）
- 主动任务目前是定时型；阈值型/事件型（如电压异常告警）已在工具层预留
- 快应用/手表生态对接（在本板无 BT 语音通路的约束下暂缓）
